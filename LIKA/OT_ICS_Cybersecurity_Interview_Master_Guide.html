Common OT Protocols

Modbus TCP: TCP/502, simple industrial read/write protocol; traditionally little built-in security.

Key point: never assume an industrial protocol is encrypted or authenticated just because it uses Ethernet.

OT / ICS Fundamentals

Industrial architecture, devices, protocols, standards, threats, and safe remediation.

What is Operational Technology?

Operational Technology (OT) is hardware and software that monitors or controls physical devices, processes, and events. Unlike normal IT, an OT compromise can affect production, machinery, safety, environmental conditions, or critical infrastructure.

Examples

  • Manufacturing assembly lines
  • Power generation and distribution
  • Oil & gas pipelines
  • Water/wastewater treatment
  • Transportation and building automation
Interview phrase: “In OT, cyber risk becomes physical risk, so security controls must account for safety, deterministic operation, availability, and engineering constraints.”

How a Control Loop Works

Physical Process ↑ ↓ Actuator Sensor ↑ ↓ PLC / Controller ↓ HMI Operator view

Sensor: measures pressure, temperature, speed, flow, level, etc.

PLC: runs logic and determines output.

Actuator: physically changes the process, e.g. opens a valve or starts a motor.

HMI: allows operators to visualize and interact with the process.

Why Availability Matters

An IT workstation can often be rebooted after a security update. A PLC controlling a production line may only be safely restarted during a maintenance window.

Bad answer: “The device is vulnerable, so I will patch it immediately.”
Better: assess exploitability and criticality; coordinate with operations; test; back up configuration; use compensating controls; patch during approved window; validate process afterwards.

ISA/IEC 62443 — Key Interview Concepts

Zone: group of assets sharing similar security requirements.

Conduit: controlled communication path between zones.

Security Level: expresses security capability/target against increasing attacker sophistication.

Practical example

Put PLCs for one production cell into a control zone, HMIs into a supervisory zone, and allow only required protocols across the conduit using an industrial firewall.

Reason: if a workstation is compromised, segmentation reduces unrestricted lateral movement toward controllers.

NIST SP 800-82

NIST SP 800-82 Rev. 3 provides guidance for securing OT while accounting for unique performance, reliability, and safety requirements.

Use it for

  • OT asset and architecture understanding
  • Threat/vulnerability assessment

  • Access control and remote access
  • Logging and monitoring
  • Incident response and recovery planning

Current final version at time this guide was created: Rev. 3; NIST also published an initial public draft of Rev. 4 in September 2026.

MITRE ATT&CK for ICS

Tactic = why the attacker performs an action. Technique = how.

ICS tactics include Initial Access, Execution, Persistence, Privilege Escalation, Evasion, Discovery, Lateral Movement, Collection, Command and Control, Inhibit Response Function, Impair Process Control, and Impact.

Vendor VPN compromised ↓ Engineering workstation ↓ Credential theft / discovery ↓ SCADA / controller access ↓ Unauthorized logic or setpoint change ↓ Process impact

Asset Inventory

You cannot protect what you do not know exists. Inventory should include:

  • Asset name/type/vendor/model
  • IP/MAC and physical location
  • Firmware/OS version
  • Owner and process criticality
  • Communication peers/protocols
  • Backup availability
  • Maintenance/support status
  • Known vulnerabilities and mitigations
OT caution: active scanning can disrupt fragile legacy devices. Use validated methods and passive discovery where appropriate.

TCP 3-Way Handshake

Client Server | ---- SYN -----------------> | | <--- SYN / ACK ------------ | | ---- ACK -----------------> | | Connection ready |

SYN: request connection. SYN/ACK: acknowledge and synchronize. ACK: final acknowledgment.

TCP provides sequencing, acknowledgments, retransmission, and flow control.

IP Address & Subnet

Example: 192.168.10.25/24

/24 means 24 network bits, mask 255.255.255.0. Typical usable hosts: 192.168.10.1–192.168.10.254.

Default gateway: router used to reach other networks.

Subnetting: divides a network into smaller logical networks; useful for segmentation and address management.

Switch vs Router vs Firewall

Switch: forwards frames inside a LAN using MAC addresses.

Router: forwards packets between IP networks.

Firewall: enforces communication policy between security zones.

In an OT design, a Layer-3 path existing does not mean communication should be allowed. The firewall should permit only required source, destination, port/protocol, and direction.

Cybersecurity Fundamentals

Risk, defense-in-depth, SIEM, incident response, vulnerability management, IAM, and OT threat detection.

CIA vs OT Priorities

Confidentiality: prevent unauthorized disclosure.

Integrity: prevent unauthorized modification.

Availability: ensure systems/services remain usable.

In OT, also explicitly consider safety, reliability, and process integrity.

Risk Formula

Risk ≈ Likelihood × Impact

For OT, impact may include:

  • Personnel safety
  • Production downtime
  • Equipment damage
  • Environmental impact
  • Regulatory impact
  • Financial/reputational impact

Defense in Depth

Physical Security ↓ Network Segmentation ↓ Secure Remote Access ↓ Endpoint Hardening ↓ Identity / Least Privilege ↓ Monitoring / Detection ↓ Backup / Recovery

Zero Trust — OT Interpretation

Do not assume a user/device is trusted simply because it is inside the network.

  • Authenticate and authorize access.
  • Use least privilege.
  • Limit trust boundaries.
  • Continuously monitor.
  • Use device/identity context where feasible.
Implementation must respect real-time and legacy OT constraints; “zero trust” is not a reason to deploy disruptive controls blindly.

Incident Response for OT

Preparation ↓ Detection / Analysis ↓ Safety + Process Impact Assessment ↓ Containment ↓ Eradication ↓ Recovery ↓ Lessons Learned

Containment must be coordinated. Isolating a controller or HMI without understanding the process can worsen an incident.

SIEM + EDR + Firewall

SIEM: centralized logs, correlation, alerts, searches, dashboards.

EDR: endpoint process/file/network telemetry and response.

Firewall: network enforcement and connection logging.

IDS/NDR: detects suspicious traffic/patterns; passive OT monitoring is often valuable.

Vulnerability Management in OT

  1. Inventory the asset and software/firmware.
  2. Validate vulnerability applicability.
  3. Assess exploitability and process criticality.
  4. Check vendor guidance.
  5. Prioritize by actual risk—not CVSS alone.
  6. Test remediation.
  7. Use compensating controls if patching is delayed.
  8. Patch during maintenance window.
  9. Validate functionality afterwards.

Compensating Controls

When you cannot immediately patch:

  • Firewall restrictions
  • Network isolation/segmentation
  • Disable unused services
  • Application allowlisting
  • Restrict admin access
  • Increase monitoring
  • Use a jump host
  • Remove Internet exposure

Example SOC/OT Investigation

Alert: engineering workstation connects to a PLC at an unusual time.

  1. Confirm asset identities and expected communication.
  2. Check whether maintenance/change ticket exists.
  3. Review user login, VPN, jump-host and privileged-access logs.
  4. Inspect network traffic and industrial protocol activity.
  5. Check EDR for new processes, scripts, remote tools, malware indicators.
  6. Determine if controller logic/setpoints/configuration changed.
  7. Coordinate with engineering/operations before containment.
  8. Preserve evidence, remediate, restore known-good configuration if required, and document.

Python Basics You Should Explain

def failed_logins(events, threshold=5):
    counts = {}
    for e in events:
        user = e["user"]
        if e["result"] == "failed":
            counts[user] = counts.get(user, 0) + 1
    return {u:c for u,c in counts.items() if c >= threshold}

SAST vs DAST

SAST: Static Application Security Testing—analyzes source/bytecode without running app.

DAST: Dynamic Application Security Testing—tests a running application externally.

SCA: Software Composition Analysis—finds vulnerable third-party dependencies/licenses.

Safe Error Handling

try:
    result = parse_config(path)
except FileNotFoundError:
    logger.error("Configuration file missing")
    raise
except ValueError as exc:
    logger.warning("Invalid configuration: %s", exc)
    raise

Do not expose secrets, stack traces, internal paths, tokens, or database details to untrusted users. Log enough for operations without leaking sensitive values.

SQL Injection

Unsafe
query = "SELECT * FROM users WHERE name = '" + user_input + "'"
Safer
cursor.execute(
    "SELECT * FROM users WHERE name = %s",
    (user_input,)
)

Use parameterized queries, validate input, and apply least-privileged database accounts.

Hard-Coded Secrets

Unsafe
API_KEY = "prod-secret-key-123"
Better
import os
API_KEY = os.environ["API_KEY"]

In production, use an approved secrets manager, rotation, access controls, and audit logging.

Authorization Review

Authentication: Who are you?

Authorization: What are you allowed to do?

A user being logged in does not automatically mean they should be permitted to change a PLC configuration, firewall policy, or another user's data.

Review permissions at every sensitive server-side action.

OT-Specific Design Review

  • Could the change interrupt the physical process?
  • What is the safe failure mode?
  • Is there manual fallback?
  • Are commands bounded and validated?
  • Can a user issue dangerous values/setpoints?
  • Can software failure affect SIS or protective functions?
  • Is a rollback plan available?
  • Was the change tested in a representative environment?

Pull Request Review Example

Scenario: A developer adds a Python API that can trigger a maintenance command on an OT device.
Review: verify strong authentication, role-based authorization, input bounds, command allowlisting, timeout/retry behavior, audit logs, no secrets in code, encrypted transport where supported, rate limiting where appropriate, failure handling, separation from safety functions, test coverage, approval/change process, and rollback behavior. Confirm the API cannot be used from untrusted networks and cannot issue arbitrary device commands.

Interview Questions & Model Answers

Technical, scenario-based, troubleshooting, secure development, and behavioral questions.

1. What is the difference between IT and OT security?

Answer: IT security primarily protects information systems and data, while OT security protects systems that monitor or control physical processes. In OT, safety, availability, reliability, process integrity, legacy equipment, and maintenance windows are major constraints. I would therefore avoid disruptive security actions and coordinate changes with operations and engineering.

2. Explain PLC, HMI, SCADA, RTU, and DCS.

PLC: industrial controller that executes logic. HMI: operator interface. SCADA: supervisory monitoring/control, often for distributed assets. RTU: remote field device used to collect/control remote process data. DCS: distributed control architecture common in plant/process environments.

3. What are zones and conduits in IEC 62443?

Answer: A zone groups assets with similar cybersecurity requirements. A conduit is the controlled communication path between zones. I use them to design segmentation so that only required communication crosses trust boundaries.

4. A critical PLC has a high-severity vulnerability. What do you do?

Answer: I would validate that the vulnerability applies to the exact model/firmware, evaluate exploitability and process criticality, review vendor guidance, and coordinate with operations. If immediate patching is unsafe, I would use compensating controls such as firewall restrictions, access limitations, segmentation, and enhanced monitoring. I would test the update, back up the controller configuration, schedule an approved maintenance window, patch, validate operation, and keep rollback available.

5. HMI cannot communicate with the PLC. How do you troubleshoot?

Answer: I would check the process impact first, then troubleshoot systematically: physical link, IP/subnet, VLAN, ARP, routing, firewall rules, port reachability, packet capture, and protocol/application state. I would compare with the known-good network baseline and avoid configuration changes without change control.

6. TCP vs UDP?

Answer: TCP is connection-oriented and provides reliable ordered delivery using acknowledgments and retransmission. UDP is connectionless with less overhead but no built-in delivery guarantee. The correct choice depends on the application requirements.

7. What happens when two devices are in different subnets?

Answer: The source recognizes that the destination is outside its local subnet and sends the packet toward its default gateway. A router or Layer-3 device determines the next hop. In a segmented OT environment, a firewall may also enforce whether that inter-zone communication is allowed.

8. What is defense in depth?

Answer: It means using multiple independent security layers so one control failure does not expose the entire environment. In OT that can include physical security, segmentation, secure remote access, least privilege, endpoint hardening, application allowlisting, monitoring, backups, and tested incident-response procedures.

9. Explain SIEM, IDS, IPS, and EDR.

SIEM: centralizes and correlates security logs. IDS: detects suspicious network activity. IPS: can block inline traffic. EDR: collects endpoint activity and supports investigation/response. In sensitive OT networks I would carefully evaluate inline blocking because false positives or device incompatibility can affect availability.

10. You see many failed logins followed by a success. What do you do?

Answer: I would not immediately assume compromise. I would identify the user, source IP, device, time, geolocation/VPN context, and authentication method; correlate with endpoint, firewall, VPN, and identity logs; verify with the user if appropriate; and investigate post-login activity. If compromise is confirmed, I would contain the account/device, reset credentials, enforce MFA, block malicious infrastructure when appropriate, and document the incident.

11. How do you review firewall rules?

Answer: I verify business/engineering need, source, destination, service/port, direction, owner, expiration where applicable, and whether a narrower rule is possible. I look for ANY/ANY rules, obsolete rules, duplicate/shadowed rules, direct IT-to-controller access, risky remote administration, and rules that bypass the OT DMZ. Changes should be reviewed, approved, tested, logged, and reversible.

12. What is a secure SDLC?

Answer: A secure SDLC integrates security into requirements, design, coding, testing, release, and maintenance. Examples include threat modeling, secure coding standards, peer review, SAST, dependency and secret scanning, DAST, signed artifacts, vulnerability response, and monitoring.

13. What do you look for during code review?

Answer: I first understand the intended behavior and changed trust boundaries. Then I review input validation, authentication, authorization, sensitive data handling, database queries, file operations, error handling, logging, secrets, cryptography, dependencies, tests, and failure behavior. For OT software, I also ask whether incorrect inputs or software failure could create a dangerous process state.

14. SAST vs DAST vs SCA?

Answer: SAST analyzes code without executing the application, DAST tests a running application from the outside, and SCA identifies third-party dependencies and known component risks. They are complementary, not substitutes for each other or for human review.

15. What is threat modeling?

Answer: Threat modeling is a structured way to understand assets, architecture, trust boundaries, possible attacker actions, and mitigations before or during development. I can use STRIDE to examine spoofing, tampering, repudiation, information disclosure, denial of service, and elevation of privilege.

16. A vendor needs remote access to an OT system. How would you design it?

Answer: I would avoid direct inbound access to controllers. I would use an approved remote-access gateway/VPN with MFA, named accounts, time-limited access, least privilege, a monitored jump host in a controlled zone, restricted destination/ports, session logging where appropriate, and a process for approval and disabling access when work is complete.

17. How would you respond to suspected malware on an engineering workstation?

Answer: I would first assess whether the workstation is actively controlling or programming a critical process and coordinate with operations. I would collect initial evidence, check EDR/process/network activity, determine whether controller changes occurred, and select safe containment. Then I would eradicate the threat, restore from a trusted source if necessary, rotate affected credentials, validate engineering software/configurations, and monitor for recurrence.

18. Why is passive monitoring important in OT?

Answer: Some legacy OT devices are sensitive to aggressive scans or unexpected traffic. Passive monitoring observes network communication without actively probing every device, helping build inventories and baselines with lower operational risk. Active scanning can still be useful when tested and approved.

19. Tell me about a Python task you could automate in security.

Answer: I could write a Python script to parse firewall or SIEM logs, extract IP addresses and users, correlate them with an asset inventory, identify repeated failed authentications or unauthorized communication pairs, and create a structured report. I would include validation, exception handling, logging, tests, and avoid automated blocking in OT unless the response action is specifically engineered and approved.

20. What would you contribute during a design review?

Answer: I would clarify requirements and data flows, identify critical assets and trust boundaries, challenge unnecessary connectivity, verify segmentation and access controls, consider failure modes and rollback, check logging/monitoring, review remote access and dependency risks, and make sure the proposed design can be operated and maintained safely.
